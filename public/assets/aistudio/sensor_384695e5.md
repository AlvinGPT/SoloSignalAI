# SoloSignal AI --- Sensor and Motion Specification

## 1. Goal

Define a realistic Android motion-sensing pipeline for a fall-detection
prototype. This file describes engineering behavior, not validated
medical thresholds.

## 2. Android sensors

### Required first sensor

-   `Sensor.TYPE_ACCELEROMETER`
-   Provides acceleration along the device's x, y, and z axes, including
    gravity.
-   Readings depend on device orientation and placement.

### Optional sensors

-   `Sensor.TYPE_LINEAR_ACCELERATION`: estimates acceleration excluding
    gravity when supported by the device's sensor stack.
-   `Sensor.TYPE_ROTATION_VECTOR`: can help estimate orientation
    changes.
-   `Sensor.TYPE_GYROSCOPE`: angular velocity, if available.

The app must check sensor availability at runtime and handle missing
optional sensors gracefully.

## 3. Data model

Each sample should contain: - Monotonic timestamp (nanoseconds from
sensor event timestamp where available). - `x`, `y`, `z` acceleration
values in m/s². - Sensor type. - Optional orientation estimate and
confidence/availability flags.

Use a monotonic clock for intervals; do not use wall-clock time to
calculate elapsed time.

## 4. Feature calculations

### Acceleration magnitude

For accelerometer components:

`magnitude = sqrt(x*x + y*y + z*z)`

With a raw accelerometer, a stationary device typically registers
gravity's magnitude. Do not interpret magnitude near gravity as proof
that the person is stationary.

### Change between samples

A simple change measure is:

`deltaMagnitude = abs(currentMagnitude - previousMagnitude)`

This is a heuristic feature, not a physical measurement of a fall by
itself.

### Windowed features

For a short rolling window, calculate: - Peak magnitude. - Minimum
magnitude where sensor semantics support meaningful interpretation. -
Mean and standard deviation. - Number and size of sudden changes. -
Change in orientation, if supported. - Movement level after the
candidate event. - Time since monitoring began and sample quality.

Use a ring buffer so memory use remains bounded. Handle dropped samples
and irregular sensor intervals.

## 5. Candidate-event logic

A transparent first version may use a state machine:

`MONITORING → CANDIDATE_EVENT → CHECK_IN → CANCELLED or ALERT_ATTEMPTED`

A candidate event should not be raised from a single acceleration peak
alone. Consider a combination of: 1. An unusual acceleration sequence.
2. A change in orientation or motion pattern, if reliable. 3. Subsequent
low movement or an unusual post-event pattern. 4. Minimum data quality
and timing checks.

The exact thresholds must be calibrated with labelled, representative
data and must not be described as medically validated. Prefer a
false-positive review screen during early testing.

## 6. Confirmation state machine

-   `MONITORING`: gather data and evaluate windows.
-   `CANDIDATE_EVENT`: freeze a short feature summary and show the
    check-in.
-   `CHECK_IN`: countdown is visible; the user can cancel or request
    help.
-   `CANCELLED`: record cancellation and return to monitoring only if
    the user left monitoring enabled.
-   `ALERT_PENDING`: attempt the configured channel.
-   `ALERT_SENT`: only after confirmed provider success.
-   `ALERT_FAILED`: show failure and a manual fallback.
-   `STOPPED`: monitoring is off; no fall detection is claimed.

Prevent duplicate alerts for the same event. Include a cooldown/re-arm
strategy and test it carefully.

## 7. Sampling and battery

-   Choose a sensor sampling rate appropriate to the device and task; do
    not assume every phone supports identical rates.
-   Avoid expensive cloud calls per sample.
-   Keep processing local and lightweight.
-   Unregister listeners when monitoring is stopped.
-   If continuous background monitoring is enabled, implement the
    required foreground service and persistent notification, and comply
    with the Android version's foreground-service and
    background-execution rules.
-   Explain battery optimization behavior to the user; never promise
    monitoring continues in every device state.

## 8. AI model policy

For an initial working app: - Use a transparent heuristic detector with
named, testable thresholds. - Keep detection logic in a separate
class. - Provide a replay/test harness for recorded sensor sequences. -
Label it as an experimental candidate-event detector.

For a later ML version: - Use a real labelled dataset that covers falls
and non-fall activities, different phone placements, ages/movement
patterns, and devices. - Split train/test data by person or session to
reduce leakage. - Evaluate sensitivity, specificity, false alarms per
hour/day, and missed-event rates. - Calibrate thresholds and document
uncertainty. - Do not use Gemini text generation as a substitute for a
trained time-series classifier.

## 9. Sensor test scenarios

Use prerecorded or synthetic traces for: - Normal walking. - Sitting
down quickly. - Lying down intentionally. - Jumping. - Phone being
placed on a table. - Phone being dropped (synthetic/recorded data
only). - A staged safe movement sequence that resembles a possible
fall. - Missing samples and noisy sensor data. - Phone orientation
changes without a fall.

Do not ask a person to perform a real fall for testing.

## 10. Required user-facing language

Use: - "Possible fall detected." - "This movement pattern may indicate a
fall." - "No response received; attempting to notify your contact." -
"Alert sent" only after a confirmed successful response. - "Could not
send alert" when the provider fails.

Avoid: - "Fall confirmed." - "You are safe." - "Emergency services have
been contacted" unless that action actually occurred and its success is
confirmed.
